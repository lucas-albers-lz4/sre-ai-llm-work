## Extracted Claims

### Claim 1: Every looped `time.After` call in the CLI was replaced with a properly cancelled timer, eliminating goroutine leaks from the timer-creation-without-cleanup pattern

- **Evidence**: PR #39188. The post explicitly identifies the pattern and the fix.
- **Confidence**: settled (specific PR, named pattern, named fix; the goroutine
  leak from looped `time.After` is a well-documented Go anti-pattern)
- **Quote**: "every looped `time.After` call in the CLI was replaced with a properly
  cancelled timer"
- **Our assessment**: In Go, `time.After(d)` creates a `time.Timer` whose underlying
  goroutine runs until the timer fires, regardless of whether the caller ever reads
  the channel. In a tight `for`+`select` loop this creates a new timer goroutine on
  every iteration, none of which are cleaned up until they fire. The fix uses
  `time.NewTimer` (or equivalent) with explicit `timer.Stop()` and channel drain
  on cancellation — the standard Go idiom for cancellable timers. For Ch02
  (Harness Engineering): the pattern is significant because CLI tools that poll
  or retry with `time.After` in loops are common in harness code; this fix
  documents the correct pattern and pairs immediately with the `timeafterleak`
  linter (Claim 2) to prevent recurrence.

### Claim 3: The `errorfwrapv` linter was auto-generated by the `linter-miner` workflow and enforced in CI — it flags `fmt.Errorf` calls that use `%v` to wrap errors instead of `%w` (PR #39263)

- **Evidence**: PR #39263. The linter's detection rule and its `linter-miner`
  origin are both stated.
- **Confidence**: settled (specific PR, named linter, quoted detection rule,
  named source workflow)
- **Quote**: "flags `fmt.Errorf` calls that use `%v` to wrap errors instead of `%w`"
- **Our assessment**: In Go, `fmt.Errorf("msg: %w", err)` wraps `err` in a way
  that preserves the error chain for `errors.Is` and `errors.As`; `%v` discards
  the chain, making sentinel error checking fail silently. The `errorfwrapv` linter
  catches this substitution at compile time. Together with `timeafterleak`, this is
  the second linter in the same week to be auto-generated by `linter-miner`,
  confirming the workflow is actively in use and producing real enforcement tooling.
  For Ch02: Go codebases using `%v` for error wrapping have a systematic
  observability and debuggability gap; `errorfwrapv` can be adopted independently
  of the gh-aw platform as a standard Go lint rule. For Ch03: error chain
  preservation is a safety-adjacent concern in agentic workflows where error types
  are used to determine retry behavior and escalation paths.

### Claim 7: Failure issues now include the last 5 tool calls as context when a tool denial triggers, enabling faster diagnosis of why an agent action was blocked (PR #39122)

- **Evidence**: PR #39122.
- **Confidence**: settled (specific PR, named context window — 5 tool calls —
  named trigger condition — tool denial)
- **Quote**: (no direct quote; see paraphrase in Our assessment)
- **Our assessment**: Tool denials in gh-aw occur when an agent attempts an
  operation that exceeds its configured permissions (e.g., a write operation
  on a read-only token, or a network call in a network-restricted workflow).
  Before this change, the failure issue would describe the denial but lacked
  the run-up context: which actions was the agent taking when it hit the
  denial? The last-5-tool-call window provides that context, enabling practitioners
  to reconstruct the agent's decision path and identify whether the denial was
  a configuration error, a prompt engineering problem, or an edge case in the
  agent's behavior. For Ch04 (Operations/Observability): this is the first
  documented use of tool-call history as a diagnostic artifact in failure
  issues — a pattern worth generalizing: whenever an agent fails on a permission
  boundary, the pre-failure action sequence is the most actionable context for
  debugging.

### Go Timer-Leak Fix Pattern (PR #39188 + PR #39133)

```go
// BEFORE (timer-leak anti-pattern caught by timeafterleak linter):
for {
    select {
    case <-time.After(timeout):
        // timer goroutine leaks on every iteration until timeout fires
        doWork()
    case <-done:
        return
    }
}

// AFTER (properly cancelled timer — pattern required by timeafterleak linter):
t := time.NewTimer(timeout)
defer t.Stop()
for {
    select {
    case <-t.C:
        t.Reset(timeout)
        doWork()
    case <-done:
        return
    }
}

// linter-miner auto-generated: timeafterleak (PR #39133)
// Flags: time.After inside for+select loops where timer would never be cancelled
// Enforcement: CI gate
```

### Error-Wrapping Lint Rule (PR #39263)

```go
// WRONG (caught by errorfwrapv linter — discards error chain):
return fmt.Errorf("failed to process: %v", err)

// RIGHT (required by errorfwrapv linter — preserves error chain for errors.Is/As):
return fmt.Errorf("failed to process: %w", err)

// linter-miner auto-generated: errorfwrapv (PR #39263)
// Flags: fmt.Errorf calls using %v instead of %w to wrap errors
```
